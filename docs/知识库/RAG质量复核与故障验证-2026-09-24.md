## 可执行评测门槛

`RagStructuredAnswerEvaluationTests` 不再只生成报告。对有知识来源的案例，它会同时断言：

1. 至少有一段逐字摘录通过服务端校验；
2. 最终交付引用中包含评测集指定的目标文档；
3. 每条引用包含文档版本、切片序号和 64 位内容 SHA-256；
4. 预期无来源的案例不能意外命中知识文档。

报告仍写入被忽略的 `target/rag-structured-answer-eval.md`，用于逐条人工判断完整性和建议是否适当。自动断言只能证明来源链条成立，不能替代人工判断回答是否充分。

## 故障验证范围

- `RagFailureChatFallbackTests` 使用真实 TCP 连接失败覆盖 Embedding 和 PostgreSQL 不可用，并用数据库超时异常覆盖检索到聊天的完整降级链路。
- `RagPostgresQueryTimeoutTests` 使用本地 PostgreSQL 真实执行慢查询，验证驱动能按超时取消。
- 两组测试合起来证明“真实超时会发生取消”和“检索异常后聊天仍完成”。当前没有在知识检索 SQL 中人为加入 `pg_sleep`，避免测试修改生产查询或知识表。

## 多意图检索实现

- `KnowledgeQueryPlanner` 只基于本轮已脱敏问题生成少量职业领域查询，不发送画像、简历或历史对话，也不增加一次大模型调用。
- 多路 Embedding 与 PostgreSQL 查询彼此独立，并行执行；结果仍按查询规划顺序逐层合并，同一文档可选取多个不同章节。
- 原始查询失败时整轮检索安全降级；单条补充查询失败时只跳过该路，不阻断其余结果。
- 当前工程的回答结构化生成继续使用 Spring AI `ChatClient.entity(...)`。查询规划没有额外调用模型，避免给检索链路增加十几秒级模型延迟。
