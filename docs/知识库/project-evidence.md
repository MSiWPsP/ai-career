# 项目实践与能力证据

## 选择项目范围

一个项目应围绕明确的用户问题和核心闭环设计，不必为了展示技术而引入所有流行组件。先明确需求、角色、关键操作和成功条件，再决定表结构、接口和页面。能稳定演示的小项目往往比功能很多但无法解释设计的项目更有价值。

## 保留工程证据

提交记录、接口测试、迁移脚本、错误日志、性能基线和部署文档可以说明工作是如何完成的。出现“性能提升”“错误率下降”等数字时，需要保留测量环境、方法和对照；没有数据时直接说明改进点和验证方式，不制造指标。

## 展示设计取舍

准备说明为什么选择某种数据模型、鉴权方式、缓存策略或异步处理。可以按“问题—候选方案—取舍—验证—遗留限制”讲述。若是团队项目，应明确自己的贡献与协作边界，不把团队成果全部归为个人。

## 复盘和迭代

每次迭代聚焦一项可以检验的改进，例如补充异常路径测试、修复慢查询或优化可访问性。把未实现的部分列为后续工作，并说明当前系统在负载、安全或运维上的限制。诚实的限制说明比笼统宣称“高并发”“企业级”更可信。
