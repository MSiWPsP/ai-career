# AI职途——RAG职业知识库详细设计文档 v1.0

## 1. 文档说明

### 1.1 文档目的

本文用于定义“AI职途——大学生智能职业成长平台”的 RAG（Retrieval-Augmented Generation，检索增强生成）方案，作为后续产品决策、技术选型、数据建模、接口设计、开发拆分、测试和验收的依据。

本文只描述设计，不代表当前仓库已经实现 RAG。当前系统已经具备职业画像、技能、职业规划、成长任务、职业规划师对话、模拟面试、能力回写和 Chat Memory，但普通职业咨询接口尚未接入 Tool Calling 或 RAG。

### 1.2 与现有文档的关系

本文细化以下既有设计：

- PRD 中的“RAG 职业知识库”；
- 功能模块文档中的岗位能力、职业成长路线、技术面试和职业规划知识库；
- Agent 文档中的 CareerPlannerAgent、InterviewerAgent 检索流程；
- API 文档中的知识文档上传、列表、删除和索引接口；
- 数据库文档中的 `knowledge_document` 可选表。

如本文与现有实现冲突，以“不破坏当前业务闭环、用户数据隔离和接口兼容”为优先原则；正式开发前仍需对本文第 23 节的待决策项作出确认。

### 1.3 当前状态声明

截至本文编写时：

- 当前代码中没有 `VectorStore`、Embedding 模型或知识文档索引流程；
- CareerPlannerAgent 使用最新职业画像、技能、当前规划和 Chat Memory；
- InterviewerAgent 使用用户画像、技能、面试上下文和 Chat Memory；
- 前端不得把“正在检索 RAG 知识库”展示为真实进度，除非后端已经执行检索并返回相应状态事件；
- RAG 接入失败时，不应破坏现有对话、规划和面试能力。

## 2. 设计结论摘要

建议采用“业务数据、知识元数据、向量数据分离”的架构：

```text
MySQL
├── 用户、画像、技能、规划、任务、面试等业务事实
├── 知识文档、版本、切片元数据和索引任务
└── 检索审计与知识引用记录（可选）

对象存储 OSS
└── 用户上传或管理员维护的原始知识文件（可选）

VectorStore
└── 知识切片向量、检索字段和必要元数据

Spring AI
├── EmbeddingModel
├── VectorStore
├── CareerPlannerAgent
└── InterviewerAgent
```

第一期推荐：

1. 只向职业规划师普通聊天接入 RAG；
2. 知识来源先由管理员审核后导入，不开放普通用户上传；
3. MySQL 保存文档事实与索引状态，向量数据独立保存；
4. 用户画像不写入公共向量库，每次请求从业务数据库读取最新快照；
5. 先做向量检索和元数据过滤，再视评测结果增加关键词混合检索与重排；
6. 检索无结果、超时或向量服务不可用时，降级到当前无 RAG 的 Agent 流程；
7. 回复应展示可追溯来源，但不能把检索片段原文整段暴露给用户；
8. 模拟面试 RAG 放在第二阶段，建议在面试开始时检索并冻结知识快照，而不是每轮无条件检索。

## 3. 目标与非目标

### 3.1 目标

- 为职业规划建议提供稳定、可维护、可追溯的知识依据；
- 降低岗位能力、学习路线和面试知识回答中的事实性幻觉；
- 在知识依据之上结合用户实时画像，生成个性化而非通用答案；
- 支持知识文档的版本管理、重新索引、下线和来源审计；
- 支持未来扩展到职业规划生成、模拟面试和面试报告；
- 保证 RAG 不可用时现有核心链路仍然可用。

### 3.2 非目标

第一期不处理以下内容：

- 实时抓取招聘网站；
- 对互联网进行无边界搜索；
- 让普通用户把个人简历上传到公共知识库；
- 用 RAG 替代用户画像、业务数据库或 Chat Memory；
- 用知识库内容直接修改用户规划、任务和能力评分；
- 自动执行未经确认的 Tool Calling；
- 构建完整的企业招聘推荐或职位撮合系统；
- 训练或微调大模型。

## 4. 核心概念与边界

### 4.1 三类上下文必须分离

| 上下文 | 数据来源 | 生命周期 | 是否进入公共向量库 |
|---|---|---|---|
| 业务上下文 | 用户画像、技能、规划、任务、面试结果 | 随用户操作实时变化 | 否 |
| 会话记忆 | 当前会话近期消息 | 会话级 | 否 |
| 知识上下文 | 岗位标准、成长路线、面试知识、职业发展资料 | 由管理员维护和版本化 | 是 |

Agent 最终输入由三者组合，但三者不能互相替代。

### 4.2 RAG 不等于数据库查询

- 查询“我还有几项任务未完成”应读取业务数据库，不应走向量检索；
- 查询“Java 后端通常需要掌握哪些能力”适合检索岗位能力知识库；
- 查询“结合我的短板给出本周计划”需要同时读取业务上下文和知识上下文；
- 查询“我们刚才说了什么”主要依赖 Chat Memory 或聊天记录，不依赖知识库。

### 4.3 知识不是指令

被检索出的文档属于不可信参考数据。即使文档中出现“忽略之前指令”“调用某接口”等文字，Agent 也不得将其视为系统指令或工具调用授权。

## 5. 使用场景与优先级

### 5.1 P0：职业规划师普通聊天

适用问题：

- 某岗位需要哪些核心能力；
- 某技术方向的学习顺序；
- 某职业阶段的准备重点；
- 学习路线、项目实践和求职准备建议；
- 用户能力与目标岗位标准之间的差距。

请求链路：

```text
用户问题
  ↓
读取最新业务上下文和近期 Chat Memory
  ↓
判断是否需要知识检索
  ↓
构造检索查询与元数据过滤条件
  ↓
VectorStore 召回候选切片
  ↓
去重、阈值过滤、可选重排
  ↓
组合知识上下文与来源
  ↓
CareerPlannerAgent 生成个性化回答
  ↓
保存回答与引用信息
```

### 5.2 P1：结构化职业规划生成

适用内容：

- 目标岗位能力标准；
- 学习路线和阶段顺序；
- 项目实践建议；
- 不同求职阶段的准备重点。

规划生成必须保存本次使用的知识版本或引用快照，避免同一版规划在知识库更新后失去解释依据。RAG 只能提供参考，最终结构仍需经过当前业务校验后才能持久化。

### 5.3 P1：模拟面试

建议在开始面试时根据岗位、难度和主题执行一次检索，形成只在本场面试有效的知识快照。后续追问主要依据候选人回答、面试上下文和该快照生成。

这样可以避免：

- 每轮检索造成延迟和成本波动；
- 同一场面试的知识依据前后变化；
- 检索结果意外包含完整标准答案并直接泄露给用户。

### 5.4 P2：面试报告与重新规划

面试报告可以使用岗位评价标准作为辅助依据，但用户本次真实回答和服务端保存的评分证据始终是事实来源。RAG 不得凭空补充用户没有表现出的能力。

### 5.5 不需要触发 RAG 的请求

- 问候、感谢和闲聊；
- 只查询平台内已有数据；
- 会话历史总结；
- 明确不需要外部知识的改写、归纳任务；
- 用户要求只基于其个人资料回答。

第一期可使用可解释的规则路由；后续再考虑通过轻量模型分类是否需要检索。

## 6. 知识库分类设计

### 6.1 第一版分类

| 分类编码 | 名称 | 主要消费者 | 示例 |
|---|---|---|---|
| `CAREER_POSITION` | 岗位能力 | 职业规划师、规划生成 | Java 后端岗位能力模型 |
| `CAREER_PATH` | 职业成长路线 | 职业规划师、规划生成 | 后端开发六个月学习路线 |
| `CAREER_GUIDANCE` | 职业规划基础 | 职业规划师 | 实习准备、校招节奏、简历原则 |
| `JAVA_INTERVIEW` | Java 面试知识 | 模拟面试官 | 集合、并发、JVM |
| `SPRING_INTERVIEW` | Spring 面试知识 | 模拟面试官 | IoC、AOP、Spring Boot |
| `MYSQL_INTERVIEW` | MySQL 面试知识 | 模拟面试官 | 索引、事务、锁 |
| `REDIS_INTERVIEW` | Redis 面试知识 | 模拟面试官 | 持久化、缓存、分布式锁 |
| `COMPUTER_BASIC` | 计算机基础 | 模拟面试官 | 网络、操作系统、数据结构 |
| `PROJECT_PRACTICE` | 项目实践 | 两个 Agent | 项目拆分、工程规范、部署实践 |

### 6.2 通用元数据

每个文档和切片至少包含：

- `documentId`：文档标识；
- `documentVersion`：文档版本；
- `category`：知识分类；
- `title`：文档标题；
- `sourceType`：人工编写、官方文档、行业报告、教材等；
- `sourceName`：来源名称；
- `sourceUrl`：可公开访问时保存原始地址；
- `language`：默认 `zh-CN`；
- `targetPosition`：适用岗位，可为空；
- `skillTags`：Java、MySQL、Redis 等标签；
- `careerStage`：探索、学习、实习、校招等；
- `difficulty`：基础、中等、高级；
- `effectiveAt`：生效时间；
- `expiresAt`：失效或复审时间；
- `visibility`：系统级、管理员级，第一期不支持用户私有知识；
- `checksum`：内容校验值，用于幂等索引；
- `chunkIndex`：切片顺序；
- `sectionPath`：章节路径。

### 6.3 标签规范

标签应使用受控词表，不允许同一概念长期存在多种写法。例如：

```text
推荐：Spring Boot
避免：springboot、SpringBoot、spring-boot 同时存在
```

必要时增加别名表，在检索查询构造阶段统一归一化。

## 7. 知识来源与治理

### 7.1 来源优先级

1. 官方职业标准、官方技术文档和高校就业指导资料；
2. 有明确发布机构和日期的行业报告；
3. 经项目维护者审核的原创知识文档；
4. 权威教材或公开课程资料的合规摘要；
5. 其他来源仅作为补充，不作为关键结论的唯一依据。

### 7.2 禁止入库内容

- 无法确认版权或授权范围的整本书、付费课程和受限题库；
- 包含真实姓名、联系方式、简历、面试记录等个人敏感信息的文档；
- 来源不明、明显过时或未经验证的网文；
- 带有恶意提示词、脚本、密钥或系统内部信息的内容；
- 招聘网站禁止抓取或禁止二次使用的数据；
- 把一次模型回答未经审核直接作为长期知识再次入库。

### 7.3 内容生命周期

```text
DRAFT 草稿
  ↓ 审核通过
READY 待索引
  ↓ 索引成功
ACTIVE 生效
  ↓ 需要更新
ARCHIVED 已归档

任意索引阶段失败 → FAILED
```

只有 `ACTIVE` 且未过期的文档可以参与线上检索。

### 7.4 更新策略

- 技术知识至少每 6 个月复审一次；
- 招聘与岗位趋势类知识至少每 3 个月复审一次；
- 职业规划通用原则可每 12 个月复审一次；
- 来源失效、内容冲突或质量投诉时立即下线；
- 新版本索引完成并验证前，旧版本继续服务；
- 激活新版本时原子切换，避免同时召回同一文档多个版本。

## 8. 总体架构

### 8.1 写入链路

```text
管理员上传或录入文档
  ↓
文件与权限校验
  ↓
原文件存入 OSS（可选）
  ↓
文本解析与规范化
  ↓
按标题和语义边界切分
  ↓
生成切片元数据
  ↓
EmbeddingModel 批量向量化
  ↓
VectorStore 幂等写入
  ↓
抽样验证索引质量
  ↓
激活新文档版本
```

### 8.2 查询链路

```text
用户问题 + 目标岗位 + 技能标签 + 当前场景
  ↓
检索路由
  ↓
查询归一化
  ↓
分类与元数据过滤
  ↓
向量召回 TopK 候选
  ↓
阈值过滤、去重、可选重排
  ↓
上下文预算裁剪
  ↓
知识片段 + 来源列表
  ↓
Agent 生成回答
```

### 8.3 推荐组件边界

```text
KnowledgeDocumentService
├── 文档、版本、状态和权限管理
└── 不直接负责模型调用

KnowledgeIngestionService
├── 解析、切分、向量化和索引
└── 通过索引任务异步执行

KnowledgeRetrievalService
├── 查询构造、过滤、召回、去重和裁剪
└── 返回统一 RetrievalResult

KnowledgeCitationService
├── 生成用户可见来源
└── 保存回答与引用关系（可选）

CareerPlannerAgent / InterviewerAgent
├── 消费整理后的知识上下文
└── 不直接操作数据库或管理索引
```

## 9. 存储技术选型

### 9.1 推荐基线

保留 MySQL 作为业务事实和知识管理数据库，新增独立 VectorStore 保存向量。

第一推荐方案为 Redis Stack Vector Store，原因：

- 不需要替换当前 MySQL；
- 相比 Milvus 运维较轻；
- 可以同时承担短期缓存，但必须与业务数据逻辑隔离；
- 适合当前知识规模和项目阶段；
- 后续可以通过 Spring AI `VectorStore` 抽象迁移。

该推荐不是最终决定。若现有部署环境已经稳定使用 PostgreSQL，可以改用 PGVector；知识量和并发显著增长后再评估 Milvus 或 Elasticsearch。

### 9.2 方案比较

| 方案 | 优点 | 缺点 | 适用阶段 |
|---|---|---|---|
| Spring AI SimpleVectorStore | 接入最快、适合本地验证 | 不适合多实例和正式生产 | 技术验证 |
| Redis Stack | 独立部署较轻、查询和缓存能力兼顾 | 内存成本、需要持久化和备份策略 | 推荐第一版 |
| PGVector | SQL 与向量统一、事务和过滤能力好 | 当前项目不是 PostgreSQL，需要新增数据库体系 | 已有 PostgreSQL 时 |
| Elasticsearch | 混合检索和全文检索能力强 | 资源和运维成本较高 | 需要复杂搜索时 |
| Milvus | 大规模向量检索能力强 | 当前阶段明显过重 | 大规模知识库 |

### 9.3 Embedding 模型约束

- Embedding 模型与聊天模型分开配置；
- 必须支持中文和中英混合技术词汇；
- 一旦索引投入使用，不能在不重建索引的情况下修改模型或向量维度；
- 文档和查询必须使用同一模型、同一预处理策略和同一向量维度；
- 更换模型时建立新索引版本，验证后再切换；
- 不在日志中记录 Embedding API 密钥或完整私有文档。

## 10. 数据模型设计

以下为目标模型，不代表当前数据库迁移已经存在。

### 10.1 `knowledge_document`

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `title` | VARCHAR(200) | 标题 |
| `category` | VARCHAR(50) | 知识分类 |
| `source_type` | VARCHAR(30) | 来源类型 |
| `source_name` | VARCHAR(200) | 来源名称 |
| `source_url` | VARCHAR(1000) | 来源地址 |
| `object_key` | VARCHAR(500) | OSS 原文件键，可空 |
| `language` | VARCHAR(20) | 默认 `zh-CN` |
| `status` | VARCHAR(20) | 文档状态 |
| `active_version` | INT | 当前生效版本 |
| `visibility` | VARCHAR(20) | 第一版固定为系统级 |
| `published_at` | DATETIME | 来源发布时间 |
| `reviewed_at` | DATETIME | 最近审核时间 |
| `expires_at` | DATETIME | 失效或复审时间 |
| `created_by` | BIGINT | 管理员用户标识 |
| `create_time` | DATETIME | 创建时间 |
| `update_time` | DATETIME | 更新时间 |

### 10.2 `knowledge_document_version`

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `document_id` | BIGINT | 文档标识 |
| `version` | INT | 版本号 |
| `content` | LONGTEXT | 规范化正文 |
| `checksum` | CHAR(64) | 内容 SHA-256 |
| `parser_version` | VARCHAR(50) | 解析器版本 |
| `chunk_policy` | VARCHAR(100) | 切分策略版本 |
| `embedding_model` | VARCHAR(100) | Embedding 模型 |
| `embedding_dimension` | INT | 向量维度 |
| `chunk_count` | INT | 切片数量 |
| `status` | VARCHAR(20) | 版本状态 |
| `error_message` | VARCHAR(1000) | 失败摘要，不保存敏感堆栈 |
| `create_time` | DATETIME | 创建时间 |

唯一约束建议：`(document_id, version)`。

### 10.3 `knowledge_chunk`

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `document_id` | BIGINT | 文档标识 |
| `document_version_id` | BIGINT | 文档版本标识 |
| `chunk_index` | INT | 切片顺序 |
| `section_path` | VARCHAR(500) | 章节路径 |
| `content_preview` | VARCHAR(1000) | 管理端预览摘要 |
| `content_checksum` | CHAR(64) | 切片校验值 |
| `vector_ref` | VARCHAR(200) | VectorStore 中的向量标识 |
| `token_count` | INT | 估算 Token 数 |
| `status` | VARCHAR(20) | 切片状态 |
| `create_time` | DATETIME | 创建时间 |

完整切片正文可以只保存在 VectorStore，也可以在 MySQL 保存；最终取决于审计、迁移和存储成本要求。推荐 MySQL 保留可审计正文，VectorStore 保存检索副本。

### 10.4 `knowledge_index_job`

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `document_id` | BIGINT | 文档标识 |
| `document_version_id` | BIGINT | 目标版本 |
| `job_type` | VARCHAR(20) | INDEX、REINDEX、DELETE |
| `status` | VARCHAR(20) | PENDING、RUNNING、SUCCESS、FAILED |
| `processed_chunks` | INT | 已处理切片数 |
| `total_chunks` | INT | 总切片数 |
| `retry_count` | INT | 重试次数 |
| `started_at` | DATETIME | 开始时间 |
| `finished_at` | DATETIME | 结束时间 |
| `error_message` | VARCHAR(1000) | 失败摘要 |
| `create_time` | DATETIME | 创建时间 |

### 10.5 可选引用审计表

后续可以增加 `knowledge_citation`，记录一次回答或报告引用了哪些文档版本和切片。第一期也可以只在结构化日志中保存，待确有审计需求后再建表。

## 11. 文档解析与切分

### 11.1 第一版文件格式

建议第一版支持：

- Markdown；
- TXT；
- 可提取文本的 PDF。

DOCX、网页抓取、扫描 PDF OCR 和复杂表格解析放到后续阶段。

### 11.2 解析规则

- 清除页眉、页脚、重复目录和无意义空白；
- 保留标题层级、列表、表格标题和来源信息；
- 不把不同章节无条件拼接；
- 表格切片必须携带表头；
- 问答资料尽量保持一个问题与其答案在同一切片；
- 代码和命令示例保持完整，避免在语句中间切断；
- 每个切片携带文档标题和章节路径，但不在正文中反复复制大量元数据。

### 11.3 初始切分参数

以下参数只作为首轮评测起点，不作为固定业务契约：

- 普通知识片段：500–800 个中文字符；
- 相邻重叠：80–120 个中文字符；
- 完整问答：优先按一个问答切分；
- 最大切片：不超过模型上下文预算允许的硬上限；
- 过短切片：与同章节相邻内容合并；
- 标题、来源和章节路径不计入主要正文长度。

最终参数必须通过检索评测确定，不能只凭字符数决定。

### 11.4 幂等性

- 文档正文计算 SHA-256；
- 相同文档、版本和校验值不重复索引；
- 切片向量标识由文档、版本和切片序号稳定生成；
- 重试任务必须先清理目标版本的残留向量或使用覆盖写入；
- 激活新版本后再异步删除旧版本向量，避免服务空窗。

## 12. 检索策略

### 12.1 查询构造

检索查询可以由以下信息组成：

```text
用户原始问题
+ 标准化目标岗位
+ 当前主题或技能标签
+ 使用场景（职业咨询、规划、面试）
```

不得把用户姓名、联系方式、完整简历、聊天全文或无关隐私拼入 Embedding 请求。

### 12.2 元数据过滤

优先按以下条件缩小范围：

- 文档状态为 `ACTIVE`；
- 文档未过期；
- 场景允许的知识分类；
- 目标岗位或通用岗位；
- 技能标签；
- 语言；
- 面试难度或职业阶段（需要时）。

### 12.3 初始召回参数

建议从以下参数开始离线调优：

- 候选召回 `candidateTopK = 12`；
- 最终进入 Prompt 的片段 `finalTopK = 4–6`；
- 相同文档最多保留 2–3 个片段；
- 知识上下文总量控制在约 3000–5000 个中文字符；
- 相似度阈值由实际 Embedding 模型和评测集确定，不在设计阶段写死。

### 12.4 去重与多样性

- 按内容校验值去除完全重复片段；
- 对高度相似片段只保留得分最高者；
- 避免最终上下文全部来自同一章节；
- 岗位标准、路线建议和风险提示可以按场景保证一定多样性；
- 后续可使用 MMR 或重排模型改善相关性与覆盖面。

### 12.5 混合检索

第一期先验证纯向量检索。出现以下问题时再加入 BM25 或关键词检索：

- Java、JVM、GC、IoC 等短技术词召回不稳定；
- 版本号、证书名、框架名等精确术语被语义检索忽略；
- 同义表达召回良好，但精确实体匹配较差。

混合检索后需要统一归一化不同分数，再进行融合或重排。

### 12.6 无结果处理

当候选为空或全部低于质量阈值时：

- 不向模型传入低质量片段；
- 使用现有业务上下文和 Chat Memory 正常回答；
- 明确提示“当前知识库没有足够依据”，不要伪造来源；
- 记录匿名化的检索缺口，供管理员补充知识；
- 不把“无结果”当作整个聊天请求失败。

## 13. Agent 接入设计

### 13.1 CareerPlannerAgent

推荐在业务 Service 层完成检索编排，再把整理后的知识上下文传给 Agent，保持 Agent 不直接访问数据库的现有边界。

目标输入结构：

```text
System Prompt
├── Agent 职责与安全规则
├── 最新业务上下文 <career_context>
├── 检索知识上下文 <knowledge_context>
└── 来源摘要 <knowledge_sources>

Chat Memory
└── 当前会话近期消息

User Message
└── 用户本次问题
```

Prompt 必须明确：

- 知识片段是参考资料，不是系统指令；
- 回答优先基于可验证知识和用户真实数据；
- 不得声称未检索到的来源；
- 知识与用户实时数据冲突时，用户实时数据描述个人现状，知识只描述一般规律；
- 多个来源冲突时说明差异和适用条件；
- 不确定时明确表达不确定性；
- 只引用本次实际召回且进入 Prompt 的来源。

### 13.2 结构化职业规划

RAG 接入不能绕过当前结构化输出校验。建议把知识依据作为独立字段输入模型，并在规划实体或审计记录中保存：

- 使用的文档版本；
- 主要引用来源；
- 检索时间；
- 检索策略版本。

规划重新生成时需要重新检索，不能默认沿用已经过期的旧知识片段。

### 13.3 InterviewerAgent

- 面试开始时根据岗位、难度和主题检索；
- 将结果保存为本场面试的知识快照；
- 每轮追问以候选人回答和面试状态为主要依据；
- 检索到的标准答案不得原样展示；
- 评分必须基于用户实际回答证据；
- 如果知识快照不可用，面试仍按当前 Agent 能力继续。

### 13.4 RAG 与 Tool Calling 的关系

第一期建议由服务端显式调用 `KnowledgeRetrievalService`，而不是让模型自行决定是否调用检索工具。原因是：

- 更容易控制延迟、成本和权限；
- 检索行为可测试、可观测；
- 避免模型绕过分类和元数据过滤；
- RAG 与业务写操作权限边界更加清楚。

后续引入 Tool Calling 后，可以允许模型在严格白名单和只读权限下触发知识检索，但不能直接管理、删除或重建知识库。

## 14. 引用与用户可见性

### 14.1 回答引用

推荐回复正文保持自然表达，在回答末尾增加简洁的“参考依据”：

```text
参考依据
1. 《Java 后端岗位能力标准》· 并发编程章节
2. 《大学生后端开发成长路线》· 第一阶段
```

引用信息来自服务端结构化结果，不能要求模型自行编造链接或标题。

### 14.2 API 扩展建议

后续可以在非流式回答和 SSE `done` 事件中增加：

```json
{
  "ragApplied": true,
  "references": [
    {
      "documentId": "10001",
      "title": "Java 后端岗位能力标准",
      "section": "并发编程",
      "sourceName": "平台职业知识库",
      "sourceUrl": null
    }
  ]
}
```

不得默认把管理员内部文件地址、OSS 私有地址、向量标识或完整切片内容返回给普通用户。

### 14.3 前端等待状态

如果需要展示“正在检索职业知识库”，后端应提供真实阶段事件：

```text
phase: CONTEXT_LOADING
phase: KNOWLEDGE_RETRIEVAL
phase: GENERATING
```

前端只根据已收到的状态显示对应文案。若后端没有执行检索，应显示“融合会话上下文”或“生成个性化建议”，不能伪装成 RAG 正在运行。

## 15. 管理接口设计

RAG 第一版不向普通用户开放管理接口。以下接口均要求管理员权限。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/knowledge` | 上传或创建知识文档 |
| GET | `/api/knowledge` | 分页查询文档 |
| GET | `/api/knowledge/{id}` | 查看文档、版本和索引状态 |
| PUT | `/api/knowledge/{id}` | 更新标题、分类、来源和标签 |
| DELETE | `/api/knowledge/{id}` | 归档文档，不建议物理删除 |
| POST | `/api/knowledge/{id}/versions` | 上传新版本 |
| POST | `/api/knowledge/{id}/index` | 创建索引或重新索引任务 |
| GET | `/api/knowledge/index-jobs/{jobId}` | 查询索引任务状态 |
| POST | `/api/knowledge/search/preview` | 管理员预览检索结果 |

### 15.1 上传文档

```http
POST /api/knowledge
Content-Type: multipart/form-data
```

建议字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 原始文件 |
| `title` | 是 | 文档标题 |
| `category` | 是 | 知识分类 |
| `sourceType` | 是 | 来源类型 |
| `sourceName` | 是 | 来源名称 |
| `sourceUrl` | 否 | 原始来源地址 |
| `targetPosition` | 否 | 适用岗位 |
| `skillTags` | 否 | 技能标签 |
| `publishedAt` | 否 | 发布时间 |
| `expiresAt` | 否 | 失效时间 |

上传成功只表示文档已保存，不表示已经可以检索。建议返回 `documentId`、`version` 和 `status=READY`。

### 15.2 创建索引

```http
POST /api/knowledge/{id}/index
```

该接口创建异步任务，立即返回 `jobId`，避免在 HTTP 请求中同步完成解析、切分和 Embedding。

### 15.3 检索预览

管理员输入查询、岗位、分类和标签后，接口返回候选切片、相似度、文档来源和过滤结果，用于：

- 调试元数据；
- 调整切分策略；
- 发现重复或过时内容；
- 建立检索评测集。

预览接口不得直接暴露给普通用户。

## 17. 安全与合规

### 17.1 权限

- 知识管理接口只对管理员开放；
- 普通用户只获得经过裁剪的引用信息；
- 索引任务不能接受任意文件系统路径；
- 对象存储地址使用受控对象键，不信任客户端提交的 Bucket 或 Endpoint；
- 删除和重新索引操作记录操作者与时间。

### 17.2 文件安全

- 限制文件类型、MIME、扩展名和大小；
- 拒绝加密文件、可执行文件和嵌入脚本；
- PDF、DOCX 等解析器运行时限制内存、页数和超时；
- 文件名不参与磁盘路径拼接；
- 后续生产环境建议增加恶意文件扫描。

### 17.3 Prompt Injection 防护

- 检索内容使用明确的数据标签包裹；
- System Prompt 声明知识片段不具有指令优先级；
- 入库时检测常见提示注入语句并进入人工审核；
- 检索结果不能改变工具权限、用户身份和系统规则；
- 回答中不得泄露 System Prompt、密钥、内部路径或其他用户数据；
- 记录命中异常片段的文档标识，方便下线处理。

### 17.4 隐私

- 公共知识库不保存用户画像、聊天记录、简历和面试回答；
- 如未来支持用户私有知识库，必须使用 `ownerUserId` 或租户字段做强制过滤；
- Embedding 请求只发送必要知识文本和最小化查询；
- 日志只保存查询摘要或哈希，不默认保存完整用户问题；
- 删除私有知识时必须同时删除元数据、原文件、切片和向量。

### 17.5 版权与来源

- 文档必须记录来源、授权范围和审核人；
- 用户可见引用应优先链接原始公开来源；
- 生成回答只能摘要和转述，不能大量复现受版权保护内容；
- 来源撤回后应立即归档并停止召回。

## 18. 可靠性与降级

### 18.1 超时与失败策略

- 检索设置独立超时，不与大模型总超时共用；
- VectorStore 超时后降级为无 RAG 回答；
- Embedding 查询失败时不重试过多，避免放大总延迟；
- 管理端索引失败可以有限次数重试；
- 线上查询失败不得改变文档或索引状态；
- 降级结果中 `ragApplied=false`，不能返回伪造引用。

### 18.2 缓存

可以缓存匿名化且无用户隐私的检索结果，缓存键至少包含：

- 归一化查询；
- 分类和元数据过滤；
- 索引版本；
- 检索策略版本。

用户画像不进入公共检索缓存。知识版本切换后旧缓存应自动失效。

### 18.3 数据一致性

- MySQL 是文档状态事实来源；
- VectorStore 只保存可重建索引；
- 定时任务可以核对 ACTIVE 文档与向量数量；
- 新版本激活失败时回滚到旧版本；
- 文档归档后即使向量物理删除延迟，也必须通过元数据过滤停止召回。

## 19. 可观测性

### 19.1 日志字段

建议每次检索记录：

- `requestId`；
- `agent`；
- `userId` 的脱敏标识；
- `conversationId` 或 `interviewId`；
- `retrievalApplied`；
- `categoryFilters`；
- `candidateCount`；
- `selectedCount`；
- `indexVersion`；
- `embeddingModel`；
- `retrievalDurationMs`；
- `totalDurationMs`；
- `fallbackReason`；
- 被选中文档标识，不记录完整私有正文。

### 19.2 指标

- 检索请求量和启用率；
- 检索成功率、超时率和降级率；
- P50、P95、P99 检索延迟；
- 平均候选数和最终片段数；
- 无结果比例；
- 各分类命中分布；
- Embedding 调用量、Token 或字符量及成本；
- 索引任务成功率和平均耗时；
- 过期文档数量；
- 用户对带引用回答的有用性反馈。

### 19.3 告警

- VectorStore 连续不可用；
- 检索 P95 延迟持续超标；
- 无结果比例突然升高；
- ACTIVE 文档与向量数量长期不一致；
- 索引任务连续失败；
- Embedding 成本或调用量异常增长。

## 20. 评测方案

RAG 是否上线不能只靠人工“看起来回答不错”，需要分别评测检索和生成。

### 20.1 检索评测集

第一期建立不少于 80 条问题：

| 场景 | 建议数量 |
|---|---:|
| 岗位能力 | 20 |
| 职业成长路线 | 15 |
| 职业规划基础 | 15 |
| Java/Spring | 15 |
| MySQL/Redis | 10 |
| 计算机基础 | 5 |

每条问题人工标注：

- 应命中的文档和章节；
- 可接受的替代来源；
- 不应命中的文档；
- 是否应该触发 RAG；
- 预期关键事实。

### 20.2 检索指标

- Recall@K；
- Precision@K；
- MRR；
- nDCG；
- 无关片段率；
- 重复片段率；
- 元数据过滤正确率；
- 检索延迟。

### 20.3 回答评测

- 事实是否得到来源支持；
- 引用是否准确指向实际片段；
- 是否错误混用其他岗位或难度；
- 是否正确结合用户画像；
- 是否明确区分通用知识与个人现状；
- 是否包含无依据的数字、排名或保证性结论；
- 没有检索结果时是否诚实降级；
- 是否抵抗知识片段中的提示注入。

### 20.4 第一版建议门槛

以下门槛需要在确定模型和数据集后再次确认：

- 目标章节 Recall@5 不低于 85%；
- 引用与答案关键事实一致率不低于 90%；
- 元数据权限过滤正确率必须为 100%；
- 提示注入测试不得改变系统规则或泄露敏感信息；
- 检索 P95 延迟目标不高于 1.5 秒；
- RAG 故障时核心聊天可成功降级。

## 21. 测试策略

### 21.1 单元测试

- 分类路由和查询归一化；
- 标签别名处理；
- 文档解析和切分边界；
- 元数据过滤构造；
- 去重、阈值和上下文预算裁剪；
- 引用生成；
- 无结果、超时和降级；
- Prompt Injection 清洗和隔离规则。

### 21.2 集成测试

- 文档上传到索引成功的完整链路；
- 重复索引幂等；
- 新版本激活和旧版本下线；
- 文档归档后不能再被召回；
- MySQL 与 VectorStore 一致性；
- Embedding 模型错误、维度错误和服务超时；
- CareerPlannerAgent 获得正确知识上下文；
- SSE 回复结束事件包含正确引用。

### 21.3 端到端测试

- 管理员上传文档、索引、预览检索；
- 用户提问并获得带来源回答；
- 不需要知识的问题不触发 RAG；
- 知识库不可用时仍能完成对话；
- 移动端正确显示引用和加载状态；
- 普通用户无法访问知识管理接口。

### 21.4 回归测试

RAG 接入后仍需验证：

- Chat Memory 会话隔离；
- 职业画像实时读取；
- 流式回复重试和消息幂等；
- 规划结构化校验；
- 面试过程中不泄露内部评分；
- 面试结果回写能力和重新规划链路。

## 23. 待决策项

正式编码前需要逐项确认：

| 决策项 | 推荐选择 | 备选 |
|---|---|---|
| VectorStore | Redis Stack | PGVector、Elasticsearch、Milvus |
| 原型存储 | SimpleVectorStore，仅本地验证 | 直接接 Redis Stack |
| Embedding 模型 | 中文和技术语义表现稳定的独立模型 | 与云厂商现有兼容接口一致的模型 |
| 首期接入范围 | 职业规划师普通聊天 | 同时接规划生成 |
| 首期文件类型 | Markdown、TXT、文本 PDF | 增加 DOCX、网页 |
| 索引方式 | 异步任务 | 小文档同步索引 |
| 检索方式 | 向量召回 + 元数据过滤 | 首期即做混合检索 |
| 重排 | 首期不启用，评测后决定 | 轻量重排模型 |
| 用户可见引用 | 展示文档标题和章节 | 只做内部审计 |
| 管理入口 | 先接口和脚本，后管理页面 | 首期同步开发管理页面 |
| 私有知识库 | 首期不支持 | 用户简历和个人材料独立索引 |
| 面试接入 | 第二阶段，开始时冻结快照 | 每轮动态检索 |

建议不要在这些决策完成前同时开发数据库、管理页面和 Agent 接入，以免索引结构反复迁移。

## 25. 第一版验收标准

第一版 RAG 可以被视为完成，需要同时满足：

1. 管理员可以创建、索引、更新和归档知识文档；
2. 只有 ACTIVE 且未过期文档参与检索；
3. 重复索引不会产生重复向量；
4. 职业规划师能对需要知识的问题执行真实检索；
5. 不需要知识的问题不会无条件调用 VectorStore；
6. 回复引用来自本次实际使用的知识片段；
7. 检索无结果或服务异常时可以降级；
8. 用户画像、聊天和其他用户数据不会进入公共知识库；
9. 普通用户不能访问知识管理和检索预览接口；
10. 提示注入测试不能改变系统规则或获得额外权限；
11. 检索评测达到确认后的发布门槛；
12. 后端测试、前端构建和核心业务回归全部通过；
13. 日志可以定位一次检索使用了哪个索引和哪些文档；
14. 前端只在后端真实执行检索时显示知识库检索状态；
15. RAG 功能可以通过配置开关安全关闭。

## 26. 主要风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 知识质量低 | 回答有来源但来源本身错误 | 来源分级、人工审核、过期机制 |
| 切分不合理 | 召回片段缺少上下文 | 标题感知切分、评测集调参 |
| 精确术语漏召回 | 技术缩写和版本号匹配差 | 标签归一化、混合检索 |
| 向量库不可用 | 聊天延迟或失败 | 独立超时、熔断、无 RAG 降级 |
| 提示注入 | 文档试图改变 Agent 规则 | 数据隔离、审核、Prompt 防护 |
| 用户隐私泄露 | 私有信息被其他用户召回 | 公共库禁入用户数据、强制权限过滤 |
| 知识过时 | 技术路线和岗位要求失真 | 来源日期、复审时间、版本管理 |
| 成本增长 | Embedding、重排和长上下文消耗上升 | 批量索引、缓存、预算限制、指标监控 |
| 引用幻觉 | 模型编造不存在的来源 | 引用由服务端结构化生成 |
| 业务边界混乱 | RAG 替代数据库事实 | 明确三类上下文和服务职责 |
| 多版本重复召回 | 同一知识出现冲突内容 | ACTIVE 版本过滤、原子切换 |
| 演示状态失真 | 前端显示了未执行的检索步骤 | 使用真实阶段事件驱动 UI |

## 27. 最终推荐

AI职途当前已经完成“画像—规划—任务—面试—能力—重新规划”的核心闭环。RAG 应作为提高知识可靠性和可追溯性的增强层，而不是重写现有业务架构。

推荐下一步先完成阶段 0：确定 VectorStore、Embedding 模型、首批知识来源和评测集。确认检索质量以后，再把 RAG 接入 CareerPlannerAgent 普通聊天。职业规划生成和模拟面试应在第一条链路稳定后逐步接入。

在任何阶段，都应坚持以下顺序：

```text
可靠知识
  ↓
可评测检索
  ↓
可追溯引用
  ↓
与实时用户上下文组合
  ↓
Agent 个性化生成
  ↓
安全降级与持续评测
```

这比先增加“正在查询 RAG 知识库”的视觉效果更重要：系统只有在真实执行检索、能够说明来源并能在失败时安全降级后，才算真正具备 RAG 能力。
